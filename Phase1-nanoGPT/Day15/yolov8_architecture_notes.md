# YOLOv8 Detection 完整架構筆記(Day15,2026-08-01)

## 整體架構:Backbone → Neck → Head

### Backbone(CSPDarknet)—— 特徵萃取

原始圖片一路 downsample(640→320→160→80→40→20),沿途抽出三層 feature map:
- 80×80(stride 8)——淺層,細節多、語意弱,適合小物件
- 40×40(stride 16)——中間層
- 20×20(stride 32)——深層,語意強、細節模糊,適合大物件

**深度不是越深越好**:沒有殘差連接(跟 nanoGPT 的梯度高速公路同理)訓練不動;深度每增加,推論變慢(yolov8n 504.6 FPS vs yolov8x 69.2 FPS,實測差 7 倍)。YOLOv8 分 n/s/m/l/x 五種大小,是速度跟準確度的取捨,不是越深越好。

### Neck(FPN + PAN)—— 特徵融合

**FPN(由深往淺)**:深層(20×20)放大跟淺層合併,語意理解往淺層傳。

**PAN(由淺往深,反向再做一次)**:淺層縮小跟深層合併,細節位置往深層傳回。

兩趟做完,三層輸出都同時具備語意+細節,不再各自偏廢。

### Head —— 偵測輸出

Neck 融合完的三層,每格中心是一個 anchor point(共 6400+1600+400=8400 個,固定位置,不是模型「找」出來,是每一個點各自獨立做預測)。

**Anchor-free 設計**:每個點預測「往上下左右各要走多遠碰到邊界框」(4 個距離值),配合 anchor point 座標即可還原出完整框(`dist2bbox`)。

## Cls loss:BCE + TaskAlignedAssigner(TAL)

**為什麼用 BCE 不用 cross_entropy**:
1. cross_entropy 假設所有類別互斥、機率加總等於 1;背景占絕大多數,互相競爭會訓練失衡
2. TAL 給的 target 是連續品質分數(如 0.6),不是 one-hot,BCE 天生適合

**易混淆點**:類別是 GT 框本身決定的(標註告訴你「這裡是狗」),anchor point 不是在多個 class 之間比較選一個。TAL 只評估「這個點夠不夠格負責這個已經確定類別的框」。

**TAL 分配機制**:
1. 候選篩選:中心點落在 GT 框內才有資格
2. 算對齊分數:`(分類信心)^0.5 × (該點目前預測框跟 GT 框的 IoU)^6.0`——注意這裡的 IoU 是「這個點目前預測出來的框」跟 GT 框的重疊度,不是點本身跟框的 IoU(點沒有面積,不能算 IoU)
3. 每個 GT 框選分數前 10 名(`tal_topk=10`)
4. 衝突處理:一點被多框選中,留給 IoU 較高者
5. 分數校正:讓 target_scores 貼近真實 IoU 品質

---

## Box loss:IoU loss + DFL

**DFL(Distribution Focal Loss)**:每個距離值對 `reg_max=16` 個離散候選值輸出機率分布,取期望值(機率×對應數值加總)還原成距離,可表達小數精度(例如 11 給 0.5、12 給 0.5,期望值 = 11.5)。訓練時只看真實答案兩側最近兩箱,用距離當權重做加權 cross-entropy,讓分布逼近「解出期望值剛好等於真實答案」。

---

## 推論後處理:NMS

1. 同類別框依信心分數排序
2. 保留最高分框,跟剩下框比 IoU,超過門檻視為重複刪除
3. 重複直到處理完,每類別各自獨立跑

**已知缺陷**:兩個真實物件靠得很近(高 IoU)會被誤刪。

**Soft-NMS**:`新分數 = 原分數 × (1 - IoU)`,重疊低的打折保留,重疊高到誇張的分數壓到接近 0 才被濾掉。

## 今天口頭複述抓到的錯誤(記錄給下次複習)

- 誤以為 anchor point 是「透過 IoU 和分數,在多個 class 之間選一個當作關注對象」——正確理解:class 由 GT 框決定,anchor point 只是被動評估夠不夠格負責這個已知類別的框
- 誤以為「anchor point 的 IoU 是多少」——正確說法:是「該 anchor point 目前預測出來的框」跟 GT 框的 IoU,點本身沒有面積不能算 IoU

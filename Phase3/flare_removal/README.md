# 曝光篩選流程(v4)

## 流程總覽

1. **上色**(`recolor_flare_images.py`):Flare7K++ 對 15,153 張 RGB 圖(train+val+test)跑去光斑推論,取 `flare`(抽出的光斑成分)輸出,依「每張圖自己的最大值」正規化,套暖色配色(黑→紅→黃→白)。
2. **黑核+光暈偵測**(`find_black_blobs.py`,函式 `find_blobs()`):
   - `BLACK_THRESH=30`:三通道都 ≤30 算「黑」
   - `MIN_AREA`:以 682x512(校準用的太陽測試圖解析度)為參考的 500px,實際套用時依每張圖真實寬高換算成相對值(見下方「v4 增量修正」)
   - 黑色 blob 不可貼圖片邊界(要被完全包圍)
   - `RING_DILATE`:以 682x512 為參考的 15px,同樣依實際圖片換算
   - `BRIGHT_RING_THRESH=80`:黑核外圍擴張範圍的平均亮度(3通道取max)門檻
   - 結果:15,153 張裡 **2,505 張**符合(這是 v4 補強後、對全部 15,153 張重新掃描的正確數字;v3 時期算出的 934 張是錯的,原因見下方「v4 補強」)
3. **排除色塊雜訊失敗品**(`blockiness_filter.py`):量化顏色後,排除純黑背景,同一色塊佔滿全圖最大連續比例 ≥0.15 就排除(JPEG 量化雜訊被正規化拉伸放大造成的假訊號)
   - 結果:2,505 → **1,994 張**(train 671、val 105、test 1,218),即目前拍板使用的最終樣本,清單見 `black_blob_summary_v4_keep.json`

## 已知但決定不處理的限制(供之後接手的人參考)

- **黑核限定(不貼邊界)是已知的範圍限制**:目前只處理「完全被包圍的黑核」,光源貼近/超出畫面邊界導致找不到完整黑核的強光曝光案例還沒處理。因為目前資料集裡沒有這類樣本,先不處理,等未來實際遇到再擴充邏輯。
- **train/val/test 比例懸殊(671/105/1,218)是已知且可解釋的**:test 集的來源影片剛好包含大量強光場景,這也是促成這次曝光篩選課題的起點,不是抽樣或邏輯錯誤,不需要調整。
- **霧夜/瀰漫散射光場景的「光暈面積」(`radial_halo_bg100` 的 halo_area_px)可能偏大、跟核心曝光嚴重度脫鉤**:因為這類場景背景本身不夠暗,radial profile 找不到清楚邊界。已驗證過用相對背景門檻、frac_reached_bg 可信度判斷都無法有效解決,且已決定不處理——把這種瀰漫光也當作光暈的一種,不特別過濾。這只影響 `halo_area_px` 數字的解讀,不影響「有沒有曝光」的核心判斷(上面的 3 步流程)。

## v4 增量修正(v3 → v4,不改變篩選邏輯本身)

### 修正 1:保留正規化前的原始強度

`recolor_flare_images.py` 當初是**原地覆蓋**、沒有備份正規化前的原始 Flare7K++ 輸出,導致要拿 raw 強度必須針對最終樣本的原圖重新跑一次模型推論(`raw_intensity_run_v4/`)。跑完用 `compute_raw_intensity_stats.py`(第一版跑840張)、後續補強後對 1,994 張全部重算,算出：

- `raw_max`:正規化前的灰階最大值
- `raw_mean`:正規化前的灰階平均值
- `raw_p95`:正規化前的灰階 95 百分位數

結果存在 `flare_intensity_raw_stats_v4.json`,已 join 進 `black_blob_summary_v4_keep.json`(用檔名比對)。1,994 張的 raw_max 範圍 28-228、raw_mean 範圍 1.0-52.3,代表即使都通過了曝光篩選,不同樣本的實際曝光嚴重程度確實有明顯差距,可以拿來做後續分級或迴歸,不用重跑模型。

**提醒**:如果之後又要對 `flare/` 資料夾做任何原地覆蓋的操作(像色調轉換、二次處理),務必先備份,否則原始強度資訊會永久遺失,像這次一樣。

### 修正 2:MIN_AREA / RING_DILATE 改成解析度相對值

掃描 `out_{train,val,test}/flare/` 這 15,153 張圖(不是原始 RGB 圖,是 Flare7K++ 模型輸出,模型會把短邊縮到 512px)的解析度分布(`scan_flare_resolution_distribution.py` → `flare_resolution_distribution.json`):

| 解析度 | 張數 | 佔比 |
|---|---|---|
| 576x512 | 5,895 | 38.90% |
| 612x512 | 4,326 | 28.55% |
| 682x512 | 3,484 | 22.99% |
| 640x512 | 1,401 | 9.25% |
| 768x512 | 47 | 0.31% |

高度 100% 固定 512(模型行為),但寬度有 5 種(576-768,最大差 1.33 倍),最主要的解析度只佔 38.9%,沒過 95% 門檻 → 改成相對值。

參考解析度取 **682x512**(校準 BLACK_THRESH/MIN_AREA/RING_DILATE/BRIGHT_RING_THRESH 這組參數時用的太陽測試圖的實際解析度):

```
MIN_AREA_RATIO = 500 / (682*512)
RING_DILATE_RATIO = 15 / hypot(682, 512)
```

套用時 `min_area_px = MIN_AREA_RATIO * (w*h)`、`ring_dilate_px = round(RING_DILATE_RATIO * hypot(w,h))`。5 種解析度換算出來的實際門檻:

| 解析度 | min_area_px | ring_dilate_px |
|---|---|---|
| 576x512 | 422 | 14 |
| 612x512 | 449 | 14 |
| 682x512 | 500(參考值本身) | 15 |
| 640x512 | 469 | 14 |
| 768x512 | 563 | 16 |

**第一次驗證方式有缺陷,已發現並修正(見下方「v4 補強」)**:一開始只拿舊的 934 張候選套用新的相對參數,確認它們沒有被踢出去,得出「差異全部是 0」的結論——但這個驗證方式測不出「有沒有新的候選應該被納入」,因為它從頭到尾都只看已經在候選名單裡的圖,對本來就沒被列入候選的圖完全沒有檢查。真正對全部 15,153 張重新掃描後,發現這個問題比預期嚴重得多,詳見下方「v4 補強」。

## v4 補強:發現 934 張候選本身就是錯的,對全部 15,153 張重新掃描

### 發現的問題

回頭檢查「修正2」的驗證方式,發現测不出真正該關心的問題:相對門檻在寬 576px 的圖片上會把 `MIN_AREA` 降到約 422px(比固定 500px 低 16%),照理說應該有一批原本卡在 422-500px 之間、階段2被排除的圖片,現在該被重新納入候選——但舊驗證只拿「現有934張候選」測,這些新增的圖根本不在934張裡,舊驗證方式看不到它們。

用 `verify_relative_threshold_v4.py` 對全部 15,153 張同時算出「固定門檻(30/500/15/80)全量重跑」跟「v4 相對門檻」兩種結果,比對後發現:

- **固定門檻全量重跑:2,399 張**(不是 934 張!)
- **v4 相對門檻:2,505 張**(比固定門檻多 127、少 21)

進一步追查發現根本原因:**v3 的 934 張,是拿舊的 1,251 張候選(用更早、更寬鬆的參數 `BLACK_THRESH=25/MIN_AREA=100/BRIGHT_RING_THRESH=180` 全量掃出來的名單)重新套用新參數過濾出來的,從來沒有對全部 15,153 張重新掃描過**。因為新參數裡 `BLACK_THRESH` 30(比25寬鬆)、`BRIGHT_RING_THRESH` 80(比180寬鬆得多),理論上能抓到一些原本連 1,251 張候選名單都沒進去的圖,而這一步從未被驗證過。實際核對:934 張裡的每一張都確實在 2,399 張的固定門檻全量結果裡(沒有矛盾),但固定門檻全量結果還多出 **1,465 張從來沒被評估過的圖片**。

### 修正結果

對 v4 相對門檻的全量掃描結果(2,505 張,`black_blob_summary_v4_raw.json`)重新走完整個階段3+4:

1. **階段3(blockiness 過濾)**:2,505 → **1,994 張**(排除 511 張色塊雜訊,`black_blob_summary_v4_stage3_fail.json`)
2. **階段4(raw 強度)**:對 1,994 張原圖重新跑 Flare7K++(`raw_intensity_run_v4/`),補上 `raw_max`/`raw_mean`/`raw_p95`

**最終樣本從 840 張修正為 1,994 張**(train 671、val 105、test 1,218),清單見 `black_blob_summary_v4_keep.json`,取代 `black_blob_summary_v3_keep.json`。

### 這次補強的教訓

任何時候「調整篩選參數」都要對**全量資料重新掃描**,不能只拿既有候選名單重新過濾——尤其當調整的參數是「放寬」某些條件時(這次是 `BLACK_THRESH` 25→30、`BRIGHT_RING_THRESH` 180→80 都變寬鬆),完全可能有本來就沒被列入候選的資料因此該被納入,只驗證既有候選集合的「有沒有被踢出去」,測不出這種「該被納入卻沒被納入」的遺漏。
